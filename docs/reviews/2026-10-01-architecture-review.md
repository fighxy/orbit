# Orbit — ревью наработок, плана и стратегии

1 октября 2026. Проверены сохранённый архитектурный документ и текущий `fighxy/orbit/main`: `8125a75264bc61310d6c7d29508dc035f1544505`. Commit совпадает с рассмотренным ранее. Это статическое ревью исходников и проектных решений. Сборка, устройство, сеть и нагрузочные тесты не запускались.

## Вердикт

Связка Rust + Kotlin Multiplatform подходит выбранному разделению ответственности. Сохраняются собственный протокол Orbit, KMP-мосты, общий Compose UI, сообщества, каналы, постоянные голосовые комнаты, голосовые сообщения, кружки и вложения.

Прежний документ полезен как карта системы, но его последовательность разработки нуждалась в изменении. Одновременно строить аналоги Hypercore/Autobase, собственный SFU, MLS-интеграцию и клиенты на пяти ОС — чрезмерно широкий первый этап. Самые дорогие неизвестные нужно проверить до подробной реализации всех библиотек.

Рекомендация: сначала небольшой работающий мессенджер с проверенным медиастеком, затем расширение собственной платформы. Цель «свой протокол на Rust» не требует собственной реализации каждой зависимости.

## 1. Подтверждённые проблемы исходного каркаса

P1 означает необходимость исправления до использования реальных аккаунтов и приватных данных; P2 — проблему, которую необходимо закрыть до соответствующего функционального этапа. Оценка относится к будущему использованию каркаса, а не к обнаруженной эксплуатации работающего сервиса.

| Приоритет | Наблюдение | Последствие | Действие |
|---|---|---|---|
| P1 | Desktop KeyStore кодирует seed через Base64 и пишет `identity.dat` | Содержимое легко восстановить из файла; комментарий про AES-GCM не соответствует реализации | Реальный OS keyring или явно спроектированное encrypted storage; при недоступности не переходить молча к plaintext |
| P1 | `Identity` содержит seedPhrase; `Message.sender` и `Room.members` используют Identity | Секрет становится частью обычных моделей; его можно случайно вывести/сериализовать | Публичная идентичность отдельно; секреты доступны только защищённым операциям |
| P1 | Desktop LocalDatabase записывает `payload.size`, а возвращает текстовые строки | Сохранить и восстановить сообщение через этот API невозможно | Реальное транзакционное хранение в Rust и round-trip/restart сценарий |
| P1 | Android/iOS KeyStore содержит TODO | Инициализация аккаунта упадёт при вызове незавершённых операций | Проверить secure-store adapter на устройстве до onboarding |
| P2 | `desktopMain` импортирует `java.*`, но от него зависят mingw/linux/macos Native targets | Этот исходный код не подходит Kotlin/Native; matrix сборки противоречит содержимому source set | JVM Compose desktop; Java/JNI actual только в JVM ветке. Native desktop включать при отдельной потребности |
| P2 | README, карта Holepunch и package.json описывают разные способы реализации | Разработчик может продолжать одновременно JS-мост и Rust-ядро | Единый ADR Rust/KMP; JS оставить только там, где нужен исследовательским инструментам |

Также не показан проверенный путь воспроизводимой сборки: в просмотренном дереве нет Gradle wrapper/root build script, а версии части plugins не заданы непосредственно в settings/shared build scripts. Не утверждаю конкретный текст Gradle-ошибки без запуска. Нужно начать с чистой сборки на CI и зафиксировать совместимые инструменты.

## 2. Существенные пробелы архитектуры

### P1 — восстановление истории из ciphertext не гарантировано

В первом плане индексы считались восстанавливаемыми из сетевого журнала. При E2EE старый ключ может быть удалён; тогда этот журнал не позволяет снова получить plaintext. Потеря «производной» локальной истории может фактически стать потерей данных.

Исправление: отдельно определить сетевой журнал, локальную защищённую историю, crypto state, attachment keys и действительно удаляемый cache. Поисковые индексы также могут раскрывать текст и должны следовать политике защиты локальной истории. Backup аккаунта не приравнивать к backup всех сообщений.

### P1 — нет атомарного контракта сообщения и crypto state

Отправка может успеть изменить ratchet, но не записать outbox. Получение может изменить ключевое состояние, но не сохранить результат. После crash повторное выполнение становится отдельной криптографической операцией с другим состоянием.

Исправление: одна транзакционная граница для crypto state, envelope, dedup и локального результата. Сначала durable commit, затем network send/ACK; retries используют сохранённые bytes. Проверить падение на каждой границе. SQLite — практичное начальное основание, но её наличие само по себе не обеспечивает корректную интеграцию crypto provider.

### P1 — ACL и MLS пока только соседствуют в схеме

Состояние прав, состав участников, временные сессии голоса и ключевые эпохи имеют разные правила. MLS не назначает владельца сообщества, publisher канала или модератора голоса. Сортировка текстовых событий не согласует конкурентные криптографические Commit.

Исправление: один уполномоченный controller для начальной политики комнаты, отдельные `policy_version` и `mls_epoch`, проверяемая связь membership update и криптографического перехода. Для более сложной модели потребуется отдельное согласование. Offline controller означает ограниченную доступность управления, которую необходимо явно принять в первой версии.

Контракт ещё предстоит проверить: late old-epoch message, revoke во время partition, rejoin, восстановление устройства и конфликтующие requests. До этого нельзя объявлять приватные группы готовыми.

### P1 — качество клиента и голос проверяются слишком поздно

В первом roadmap клиенты и голос появлялись после большого объёма инфраструктуры. Для продукта с Discord-подобными комнатами наличие подходящего WebRTC adapter, desktop binding, audio routing и корректного iOS lifecycle — фундаментальные зависимости.

Исправление: минимальный Compose экран сразу. Ранний отдельный опыт: три устройства входят в одну комнату; затем interruption, background, Bluetooth и смена сети. Это не означает одновременную разработку всех функций: эксперименты ограничены вопросами, от которых зависит дальнейшая архитектура.

### P2 — журнал всего устройства смешивает границы доступа

Единый реплицируемый stream устройства с сообщениями из всех комнат усложняет выборочную выдачу, обработку недоступных предшественников и защиту метаданных.

Исправление: логическое разделение по `(scope_id, device_id)`. Можно хранить всё в одной DB; сетевой протокол читает только разрешённый scope. Для приватной доставки внешний routing envelope не должен раскрывать всю публичную идентичность и структуру комнат без необходимости.

### P2 — собственный SFU недооценён как отдельный продукт

str0m подходит для исследования Rust media server. В документации есть SFU example, но авторы прямо предупреждают о его непригодности для production и тяжёлой нагрузки. Библиотека не включает полный клиентский pipeline capture/encode/decode и адаптивный jitter buffer.

Исправление: готовый self-hosted SFU для контрольного сценария; Rust-SFU сравнивается с ним позже. LiveKit — кандидат, его сервер написан на Go. Это осознанная сторонняя зависимость и рекомендация ревью, не замена согласованного Rust-ядра. Поддержку каждого KMP target ещё нужно проверить.

### P2 — мгновенный отзыв прав не следует из подписанного ticket

SFU с устаревшей политикой может продолжать принимать ранее выданный ticket. Offline участник P2P комнаты может ещё не знать об отзыве.

Исправление: ограниченное время действия ticket, источник свежей policy, revocation messages, закрытие активной сессии и явно заданное поведение при недоступности authority. Для P2P фиксируется допустимая задержка/граница принятия событий. Подпись доказывает авторство разрешения, но не его актуальность.

### P2 — polling и число сервисов пока не обоснованы

Частый опрос FFI увеличивает число пробуждений, особенно на телефоне. Немедленное разделение mailbox/node/push на отдельные развёртывания добавляет эксплуатацию до появления нагрузки.

Исправление: cancellable event wait на worker, пакетные события и snapshot recovery. На старте один `orbit-node` может содержать логически разделённые функции; media server отдельно. Самостоятельные процессы и crates выделяются по реальным границам и измерениям.

## 3. Что оставляю из прежнего плана

- Rust владеет данными, протоколом и правилами; KMP — клиентским состоянием, интерфейсом и платформенными службами.
- Одна база под управлением Rust; Kotlin не создаёт независимое хранилище тех же сообщений.
- KMP commonMain API и platform actuals: JNI для JVM, C interop для iOS. Это корректное направление; ABI/lifetime остаются работой проекта.
- Текстовый чат, broadcast channel и постоянная voice room имеют разные модели прав.
- Voice note/video note — файловые сообщения; real-time audio имеет отдельный transport.
- Relay, mailbox, push и SFU различаются по функции, даже если часть служб живёт на одном сервере.
- Публичные каналы и приватные группы имеют разную модель доступа; требование Telegram-подобного UI не задаёт автоматически их криптографию.
- Готовые crypto/transport/media dependencies допустимы. Собственный протокол означает свои схемы и правила приложения.

## 4. Исправленная последовательность

| Шаг | Что пользователь сможет проверить | Что должно быть решено |
|---|---|---|
| 0 | Устанавливаемый KMP клиент, запускающий Rust | Сборка, targets, ABI, close/cancel и secure store |
| 1 | Два маленьких demo: приватное сообщение и голос на трёх устройствах | Transport/relay, E2EE persistence, client media adapters, lifecycle |
| 2 | Реальный личный чат после перезапуска и offline | DB/outbox/mailbox, статусы доставки, ключи и минимальный UI |
| 3 | Постоянная голосовая комната сообщества | Join/leave, mute/deafen, reconnect, реальные аудиоустройства |
| 4 | Канал с публикациями и подписчиками | Publisher permission, подписи, история и управляющий поток |
| 5 | Файл/фото, голосовые, затем кружки | Cache, chunks/resume, capture и playback на целевых ОС |
| 6 | Приватная группа и несколько устройств | ACL/MLS переходы, revoke, rejoin, history transfer и backup |
| 7 | Расширенная платформа | Остальные targets, обсуждения, роли, эксплуатация и нагрузка |
| 8 | Собственный Rust-SFU и более сложная репликация при необходимости | Измеримое преимущество и совместимость с проверенными сценариями |

Ранний фокус испытаний — iOS, Android и одна desktop ОС. Остальные платформы сохраняются в цели и получают CI smoke сборки рано. Не обещать, что iOS результат доказывает готовность Windows/Linux media integration.

Не все функции нужно включать в первую альфу. Для полезного первого выпуска достаточно личного чата, одного типа сообщества, ленты канала, базовой голосовой комнаты и файлов; остальные форматы используют проверенную инфраструктуру следующими шагами.

Детальная декомпозиция предыдущего плана сохранена в редакции 2 как возможная целевая структура. Семь crates сами по себе не ошибка. Ошибка стратегии — считать их полную реализацию условием первого пользовательского сценария.

## 6. Решения, которые пока остаются открытыми

1. Конкретные transport/crypto/media библиотеки и версии после PoC.
2. Авторизация membership updates и mapping между политикой Orbit и криптографическими переходами.
3. Выдача старой истории новому участнику, перенос на новое устройство, потеря всех устройств.
4. Media E2EE и управление ключами на всех targets; SFU transport encryption недостаточно для такого обещания.
5. Пределы участников голоса, размеров файла и приватного канала; SLA доставки и срок хранения.
6. Модель self-hosting и кому принадлежит постоянно доступный community/controller endpoint.

Не требуется остановить всю работу до ответов на все пункты. Сборку, KMP UI, FFI lifecycle и транспортный эксперимент можно выполнять сейчас. Реализация приватных групп зависит от пунктов 2–3, а обещание E2EE голоса — от пункта 4.

## 7. Критерии оценки стратегии

Успех измерять не количеством переписанных пакетов. Проверять отсутствие потери подтверждённых сообщений, восстановление после crash/reconnect, корректность прав, работающий звук и плавность интерфейса на настоящих устройствах.

Рекомендуемые задачи для первого измерения: 1000 сообщений с duplicates/restart; прерванная передача файла; 30 минут голоса на трёх устройствах; несколько смен сети; перезапуск клиента и повторный вход в голос. Это предложенные сценарии, они в этом ревью не выполнялись.

Отдельно измерять батарею, время до первого звука, reconnect, трафик SFU/relay, объём history/blob storage. Пример оценки SFU egress: N слушателей × K получаемых каждым слушателем потоков × средний bitrate, плюс overhead. Конкретные стоимость и серверный sizing можно считать после измерений.

## Источники технической проверки

- [RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html) и [MLS Architecture RFC 9750](https://www.rfc-editor.org/rfc/rfc9750.html): криптографическое состояние, эпохи и обязанности приложения. Предлагаемая политика Orbit — инженерное решение, не готовая функция RFC.
- [str0m](https://github.com/algesten/str0m): ограничения клиентских функций и production-статуса SFU example.
- [LiveKit server](https://github.com/livekit/livekit): готовая SFU реализация на Go; [encryption](https://docs.livekit.io/transport/encryption/): отдельно управляемое media E2EE, ключи и видимость сигналинга.
- [Kotlin/Native C interop](https://kotlinlang.org/docs/native-c-interop.html): платформа для KMP bridge.
- [SQLite atomic commit](https://www.sqlite.org/atomiccommit.html): транзакционное основание; конкретные настройки durability и crypto integration должны быть проверены приложением.

Результаты относятся к рассмотренному commit. Исполняемый код в рамках этого статического ревью не изменялся. Уточнённые решения включены в [архитектуру](../architecture/rust-kmp.md), а порядок внедрения — в [roadmap](../roadmap.md).
