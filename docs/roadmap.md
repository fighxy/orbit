# План реализации Orbit

Статус: план после архитектурного ревью от 01.10.2026. Все пункты ниже открыты.
Технические кандидаты становятся зависимостями только после соответствующего
эксперимента. Документ не содержит результатов выполненных сборок или испытаний.

Основание: [ADR 0001](adr/0001-rust-core-kmp-clients.md),
[архитектура](architecture/rust-kmp.md),
[ревью исходного каркаса](reviews/2026-10-01-architecture-review.md).

## 0. Воспроизводимая и безопасная база

- [ ] Зафиксировать toolchain и воспроизводимую Gradle/Cargo сборку; добавить wrapper и CI.
- [ ] Разделить JVM desktop и Kotlin/Native source sets; убрать Java API из Native target graph.
- [ ] Создать минимальные `crates/orbit-core/` и `crates/orbit-ffi/`.
- [ ] Сделать KMP `NativeEngine` с Android/JVM JNI и iOS cinterop.
- [ ] Добавить минимальный Compose экран и платформенные entry points.
- [ ] Разделить публичные identity DTO и секреты; убрать seed из sender/member models.
- [ ] Заменить Base64 key storage и TODO реальными secure-store adapters; исключить молчаливое plaintext fallback.
- [ ] Заменить хранилище, записывающее только длины payload, реальным storage под управлением Rust.
- [ ] Проверить необходимость исторического root `package.json`; убрать его из runtime пути и перенести в reference tools либо удалить при отсутствии потребителя.

Критерий: чистая сборка устанавливается на iOS device/simulator, Android и одну
desktop ОС, вызывает Rust и корректно закрывает engine. Данные storage проходят
round-trip после restart. Подключены smoke сборки остальных заявленных targets.

## 1. Ранние эксперименты архитектуры

- [ ] Проверить data transport direct/relay, смену сети и восстановление соединения.
- [ ] Проверить FFI ownership, cancel/close races, event wait и snapshot recovery.
- [ ] Испытать E2EE-кандидат для двух устройств, crypto-state persistence и crash recovery.
- [ ] Провести голосовой эксперимент на трёх устройствах через готовый self-hosted SFU.
- [ ] Проверить media adapters на iOS, Android и desktop: устройства ввода/вывода, interruptions, Bluetooth и lifecycle.
- [ ] Зафиксировать выбранные версии, результаты и причины выбора в отдельных ADR.

Критерий: самые существенные зависимости подтверждены работающими программами
на реальных targets. Отсутствующий desktop media binding или ненадёжный storage
решается здесь, до полной реализации UI и собственной инфраструктуры.

## 2. Личный чат

- [ ] Один аккаунт и одно устройство с устойчивой публичной идентичностью.
- [ ] Проверяемое приглашение с ожидаемой идентичностью второй стороны.
- [ ] Минимальный chat list, история и composer на KMP.
- [ ] Транзакционная запись crypto state, окончательного ciphertext и outbox.
- [ ] Dedup, retry того же envelope, durable получение и корректные ACK.
- [ ] Логические streams по scope/device, авторизация доступа к scope.
- [ ] Mailbox с ciphertext, capability, TTL и квотами.
- [ ] Различимые статусы: локальная очередь, сохранение mailbox, получение адресатом.

Критерий: сообщение проходит между двумя устройствами через direct/relay и
offline delivery; restart не теряет подтверждённые данные и не меняет уже
сформированный ciphertext. Повреждение storage не скрывается успешным статусом.

## 3. Постоянная голосовая комната

- [ ] Community и сохранённое описание VoiceRoom.
- [ ] Отдельная временная VoiceSession и контракт авторизации входа/выступления.
- [ ] Join/leave, mute/deafen, выбор аудиоустройства, индикация говорящего.
- [ ] Session ticket с проверяемой свежестью, reconnect и завершение отозванной сессии.
- [ ] Нагрузка файлов не блокирует управляющий и медиатрафик.
- [ ] Ограничения background/audio lifecycle явно отражены в состоянии клиента.

Критерий: три клиента разговаривают в одной комнате, корректно возвращаются
после потери связи и обрабатывают смену audio route. Media E2EE не объявляется
готовым без отдельной проверки SDK и распределения ключей.

## 4. Канал и базовое сообщество

- [ ] Разделить Conversation, BroadcastChannel, Community и VoiceRoom.
- [ ] Один controller политики и роли owner/publisher/subscriber.
- [ ] Подписанные публикации с устойчивым PostId; edit/delete как проверяемые события.
- [ ] Подписка и загрузка истории без full mesh всех подписчиков.
- [ ] Проверка прав на стороне core/получателей и обслуживающих служб.

Критерий: автор публикует, подписчик получает историю и не может опубликовать
собственный пост с правами автора. Управляющий поток имеет однозначного
уполномоченного писателя. Приватность канала требует отдельной схемы ключей.

## 5. Вложения и записанные медиа

- [ ] Сначала File/Photo: durable manifest/blob, upload/download, cancel/resume, integrity.
- [ ] Затем VoiceNote: capture, duration, waveform и playback.
- [ ] Затем VideoNote: capture, preview, rotation и круглая маска UI.
- [ ] Проверить codec/container на всех целевых платформах.
- [ ] Разделить cache eviction, retention истории, attachment keys и backup.
- [ ] Ограничить размер, duration, разрешение и auto-download.

Критерий: импортированный и записанный файл воспроизводится после restart и
прерванной передачи; временный локальный файл не выдаётся за доступное другим
участникам вложение. Превью защищены согласно политике исходного сообщения.

## 6. Приватные группы, устройства и восстановление

- [ ] Определить связь policy_version, membership changes и MLS epoch.
- [ ] Зафиксировать authority, Commit/Welcome, late old-epoch events и partition policy.
- [ ] Проверить отзыв устройства, недоступность controller, rejoin и ограничения устаревших tickets.
- [ ] Спроектировать выдачу истории новому участнику и перенос на новое устройство.
- [ ] Разделить восстановление account authority и резервную копию истории/ключей.
- [ ] Проверить crash между decrypt/encrypt и durable записью всех связанных состояний.

Критерий: разрешения и история сходятся по описанной политике; невозможно получить
право администратора только за счёт membership в криптографической группе.
Недоступность старых ключей обрабатывается без обещания восстановления plaintext
из одного сетевого ciphertext.

## 7. Расширение и эксплуатация

- [ ] Полноценные продуктовые проверки Windows, Linux и macOS сверх ранних smoke builds.
- [ ] Push integration и foreground resync независимо от успешности фонового push.
- [ ] Обсуждения публикаций, расширенные роли и moderation по отдельным требованиям.
- [ ] Fuzz/limits, метрики reconnect, батареи, памяти, storage и сетевого трафика.
- [ ] Определить лимиты участников, файлов, retention и режимы self-hosting.

Критерий: измерены эксплуатационные пределы и понятны издержки SFU/relay/blob
delivery. Испытания и защиты не откладываются целиком до этого этапа: каждый
предыдущий шаг закрывает собственные риски данных, ошибок и жизненного цикла.

## 8. Собственная инфраструктура и выделение библиотек

- [ ] При обоснованной потребности сравнить Rust-SFU/str0m с проверенным baseline.
- [ ] Добавить sparse/Merkle replication при необходимости, подтверждённой измерениями.
- [ ] Выделять crates из orbit-core по устойчивым границам и повторному использованию.
- [ ] Разделять процессы node/mailbox/push только при эксплуатационной необходимости.

Критерий: замена проходит тот же набор клиентских сценариев и даёт конкретное
преимущество. Количество перенесённых пакетов Holepunch не является метрикой
готовности мессенджера.
